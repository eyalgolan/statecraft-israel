## Summary for the owner

1. **Almost every GDD system is new.** The sim has no units, cities, jobs, training, construction, movement, combat or
   settlement control. The military today is one ladder rung and one call-up number (`GameState.cs:38-40`). What carries over is the
   machinery: the deterministic step, the single RNG, the canonical hash, saves as command logs, content windows, the
   event system and its cards, the cabinet, the treasury and the immigration series.
2. **Monthly turns are cheap to build.** Their cost is the golden churn. The cadence is one function
   (`SecuritySystem.TurnLengthFor`, `SecuritySystem.cs:9-10`), and #81 already designs a `turn_lengths` rules key for it.
   But it moves every golden. The 31 event windows were also tuned so each decision opens "on the turn before" on weekly war turns
   (determinism.md, rebaseline row "playtest 1 E fix 1"), so the windows must be re-timed. The fx-crisis calibration may need refitting too
   (`rules.yaml:39-51`).
3. **Build behind a switch, then cut over once.** New state is hashed only when it is not at its default (chapters
   spec §8, item 4). So Phase 1 can land with `Hash1950`, `Hash1952`, `smoke5` and the scenario goldens unmoved, and
   in-flight PRs keep passing. A single cutover PR then switches to monthly turns and the GDD loop and rebaselines everything, for a
   stated reason.
4. **The biggest risk is sensitivity, not code.** Raid, occupy and deport on real, named Arab localities turns
   presentation-only data (`localities_1948.yaml`, 1,096 rows) into gameplay targets. §4 gives the minimum rules that keep the
   owner's ruling "honest cost, no reward" from being broken by a loophole: a deported settlement's empty houses, deportees
   counted as player refugees, or prisoners used as labour.
5. **Phase 1 is blocked by four decisions** (§5, group A): what a unit is (D-A1), how civilians are assigned (D-A2),
   instant or multi-turn work (D-A3), and the slice's city, site and objective card (D-A4). Every other open item can wait for its own
   phase.

## 2. Architecture

Principles kept from AGENTS.md and docs/determinism.md:
- rules live in `sim/Statecraft.Sim` (netstandard2.1);
- Unity only draws and sends commands;
- one SplitMix64 RNG in `GameState.RngState`;
- no trigonometry;
- no unordered iteration into state;
- a canonical SHA-256 hash.

### 2.1 The switch

Add one era switch next to the existing ones (`EraSystems`, `Content.cs:42-51`; read by `SystemsAt`, `Content.cs:424`):
`systems: { loop: gdd }`, defaulting to `legacy`, and the `turn_lengths` rules key from #81.
- Before cutover, the real `eras.yaml` keeps the defaults. Tests load the real content with an in-memory overlay that turns the
  switch on. `ContentLoader` already takes a `readFile` function, and `Preview.LoadWith` (`Preview.cs`) does the same for
  rules. That is how the new MVP goldens are pinned before cutover.
- Cutover flips the real file (§3).

This gives one code path per system, with a branch at the system's entry, not two simulations.

### 2.2 State shape

All new collections are **ordered by id** (ordinal), hold **immutable** records replaced on change (the `Placement` and
`Appointment` pattern, `MapActions.cs:8-15`, `Cabinet.cs:9-14`), and use **integers** for counts, strengths, progress and
timers. Doubles stay only for the 0–1 national parameters and Money. So `Clone()` stays shallow per collection
(`GameState.cs:61-77`), and no floating-point sum depends on dictionary order. The chapters spec §7 flags exactly that risk for
`TotalPopulation`.

```
GameState (new fields; all omitted from the hash text while empty or at default)
  int     Arms; int Food                          national pools (D-C2); Money = Treasury
  int     NextUnitId                              ids never reused
  SortedList<int, Unit>          Units            Unit: Id, Type, Side, Q, R, Count, Order, OrderTarget,
                                                  TurnsLeft, Experience, Strength, Home(city id)
  SortedDictionary<string, City> Cities           City: HousingCapacity, HousingCondition, JobSlots,
                                                  Residents by role (if pooled, D-A2), Control
  SortedDictionary<string, Site> Sites            Site: State (available|in_progress|built), Progress
  SortedDictionary<string, Corridor> Corridors    Corridor: segment progress[] (int)
  List<Project> Projects                          Project: Id, Kind, City|Site|Corridor, TurnsLeft, Workers
  SortedDictionary<string, Control> Settlements   Control: Owner, State (hostile|raided|occupied|puppet|
                                                  annexed|depopulated), Since, Residents, Combatants,
                                                  Buildings (intact|damaged|razed)
  SortedDictionary<string, Objective> Objectives  Objective: CompletedOn (date) or null
  int     Score; int PrisonersHeld; int PrisonersReturned
  int     DisplacedByPlayer                       the permanent record Deport writes (§4.1)
```

The content side adds sim-read files, each inside the content hash:
- `unit_types.yaml`: stats, training, upkeep and `art_type`;
- `cities.yaml`: start values, sourced or labelled as assumptions;
- `sites.yaml`;
- `corridors.yaml`;
- `projects.yaml`;
- `objectives.yaml`: historical date, sources, image and text;
- `scenario_1948.yaml`: starting units and the enemy script.

The loader validates every id and hex, like `settlement_hexes.yaml` today.

### 2.3 Commands and the order of resolution

**Standing orders, not per-turn orders.** A unit keeps its order (working, training, building, fortified, holding,
attacking) until the player changes it. Commands are only *changes*, so a 48-turn save stays small and replays fast.

Proposed commands, each with a `Kind` key in `attention_cost`:

| Command | Effect at command time (validated, refused with a reason as today) |
|---|---|
| `AssignWork(unit, city, role)` or `AssignWorkers(city, role, n)` (D-A2) | Takes a job slot or leaves one |
| `Train(unit, facility)` | Starts basic training (camp) or pioneer training (Hakhshara). The number of turns is open |
| `Move(unit, q, r)` | Moves along a path the sim computes (BFS over hexes, neighbours in a fixed order, no trigonometry) within the allowance |
| `UnitOrder(unit, fortify / hold / attack, q, r)` | Sets the order. An attack resolves in the resolution phase |
| `StartProject(kind, city or site or corridor)` | Commits Money and workers |
| `PioneerWork(unit, action, target)` | Road or rail segment, plow, dry swamp, build yishuv, build a camp |
| `ResolveCapture(settlement, raid / occupy / deport)` | Only on a settlement the player has just captured (§4.1) |
| `EndOccupation(settlement, puppet / annex / withdraw)` | After X turns. Whether withdrawal is allowed is open |

**Resolution phase.** This is a new `TurnResolver`, called from `Simulation.Step` after `EventSystem.Delegate` (`Simulation.cs:53`)
and before the existing systems. The order is fixed and each step gets a rule ID (docs/rules/README.md):
1. the enemy's orders, computed from the state (Historical mode follows a sourced script where one exists);
2. combat, in ascending attacker id, with a documented number of RNG draws each;
3. capture checks;
4. training;
5. construction;
6. production (Money from jobs, Food from fields);
7. consumption (Food, Arms and Money upkeep, and prisoners' food);
8. housing and shortages, then Social cohesion;
9. arrivals (the immigration series becomes units);
10. occupation timers;
11. objectives and score.

The GDD leaves the resolution order open, so this is a proposal (D-A6). Any new RNG draw shifts every later draw in the turn. That
is expected, and it moves goldens.

Every command kind needs the same five touches:
- `AttentionSystem.Kinds` (`AttentionSystem.cs:9-10`);
- `CommandText.Validate`, which throws on an unknown type (`Commands.cs:79-92`);
- the save line in `SaveGame.Format` and `ParseCommand` (`SaveGame.cs:85`, `:141`);
- the test scenario kinds (`Scenario.cs:66-83`);
- the Unity queue's `Key` and `Validate` (`SimBridge.cs:42`, `:64`). Its default refuses silently with `order.invalid`, so add a
  reflection guard like the sim's.

`HistoricalAI` (`HistoricalAI.cs`) answers only events and the call-up. The goldens need a **reference player** for the new
loop: a deterministic policy, for example fill job slots, then send a fixed share to training, then take the next designated
site. That policy is test code, not game rules, and it should be named so (D-A7).

### 2.4 Hash and saves

- **Hash.** New sections are added to `CanonicalText` (`GameState.cs:93-150`) after `over=`, **only when non-empty**: `res{}`, `units[]`,
  `city{}`, `site{}`, `corr{}`, `proj[]`, `ctrl{}`, `obj{}`, `score=`. With the switch off, the text is byte-identical to today.
  This is chapters spec §8, item 4. `Describe()` shares the writer, so snapshot diffs show the new sections by name.
- **Saves.** Bump to schema 2 (`SaveGame.cs:30`) for the new command lines, and add a `ruleset gdd-0.1` header line.
  - A schema 1 save after cutover would replay under different rules and drift. It is refused with a clear player-facing message ("made with
    an earlier version of the game's rules; start a new game"). The content-hash warning is not enough, because the rules changed, not just the content.
  - The chapter checkpoints (#64, deferred) take schema 3 if they are ever built.
  - `MaxTurns = 2000` (`SaveGame.cs:32`) is unaffected.

### 2.5 Performance at MVP scale

- **Measured today:** 43 turns play in 5–10 ms (chapters spec §2).
- **The MVP:** about 48 turns, 25 cities (`settlements_1948.yaml`) plus some tens of sites, 870 land hexes, and at most some
  hundreds of units if units are groups (D-A1).
- **Per turn:** BFS on 870 hexes per moving unit and one pass over units and cities. That is microseconds to low milliseconds.
- **Hash:** a units section of about 300 × 60 bytes is about 18 KB of SHA-256 input a turn. That is negligible, but the hash runs every turn in
  `SaveGame.Record`.
- **Budgets:** a full 48-turn golden under 200 ms on .NET, and one `Step` under 16 ms in the WebGL player.
- **The risk is LINQ allocation in hot loops.** Keep the resolver allocation-light, as the map-label performance test demands of the UI.
- **If each unit were one person**, the population would be about 650,000 units (`rules.yaml:61`). That is impossible, which is part of why D-A1 matters.

### 2.6 How presentation reads the new state

- **Units in play.**
  - `UnitRoster` (`UnitRoster.cs`) gains a sibling that builds tokens from `State.Units`, grouped per hex. The token, badge,
    figure count, card and the authored-prefab hook (`unity/Assets/Resources/Units/Authored/<art type>`) are unchanged.
  - The art type comes from `unit_types.yaml`.
  - The sim hex becomes authoritative. `UnitPlacer`'s one-hex presentation offset stays only to clear town kits and roads.
  - `units_1948.yaml` brigade anchors can seed Historical starting positions (moving them into the content hash at that point).
- **Kits.**
  - Completed projects keep drawing through `PlacementLayer` (`GameRoot.cs:313-320`).
  - Later, housing condition can pick kit variants.
  - A new yishuv draws a rural kit at its site.
- **Routes.** `RouteLayer` already shows routes by date. Corridors under construction draw only their built segments, from sim
  progress, on the traced geometry.
- **UI.**
  - A city panel (housing, jobs, projects).
  - A unit card with orders. Today it has none and links to the Defence screen.
  - An objectives panel.
  - A capture dialog with the sober cost preview §4.1 requires.
  - Every preview number (reachable hexes, cost and time) comes from a sim helper, as with `EffectiveMobilization` today (m3-rulings, "Shared rules are public sim helpers").

## 3. Determinism and goldens: the rebaseline plan

**Before cutover (Phase 1).**
- All new state is omitted at its default, and the switch is off in the real content. `Hash1950`, `Hash1952`, `smoke5`,
  `scenario-cautious` and `scenario-reckless` (`golden/manifest.txt`) **do not move**.

## 4. Content and sensitivity

### 4.1 Deport: honest cost, no reward (minimum specification)

This follows owner ruling 1 and CONTENT_POLICY §4 ("never pays").

1. **Only on capture.**
   - Deport is offered only in the capture dialog of a settlement the player has just taken.
   - It is never the default, never first in the list, never pre-selected, and never chosen by the reference player or by delegation.
   - `HistoricalAI` and the reference player choose Raid or Occupy.
   - Historical mode does not force it.
2. **Costs, all large.**
   - Social cohesion and International Support fall at once (values are game balance, set by the owner).
   - A **permanent** International Support drag lasts for the rest of the game, recorded in `DisplacedByPlayer`.
   - Then follow-up event cards (below).
3. **Refugees.**
   - The residents become a displaced population **outside the player's control**. They are counted in `DisplacedByPlayer` and feed the
     `arab_refugees` actor (`model.yaml:49`) once diplomacy exists.
   - They are **never** the GDD's player-side "Refugee" units, and never labour, housing occupants or score.
4. **No reward, by construction.**
   - A deported settlement becomes `depopulated`:
     - it adds no housing capacity, jobs, Food, Money, Arms or score;
     - it cannot be puppeted or annexed for gain;
     - it counts towards no objective;
     - it ends the Occupy timer.
   - Whether its buildings stand is a separate rule (the GDD separates deportation from razing; D-F3). Either way they are not usable housing in the MVP.
5. **Tests that enforce it** (in `dotnet test`, like the atrocity rule today, `EventRules.cs:78-79`):
   - `DeportNeverDominates`: from any state where it is offered, Deport's outcome is less than or equal to Occupy's and Raid's on every resource, parameter and score, at the end of the turn and at the MVP end. This is a property test over the golden runs' capture states.
   - Event options tagged `displacement` (a new sensitive tag in `EventRules.SensitiveTags`, `EventRules.cs:11`) cannot have a positive effect on any of Money, Arms, Food, Social cohesion, International Support or score. This extends the treasury and fx rule to all five resources.
   - Every event with the tag needs `sensitivity-reviewed` before a shareable build (`ReleaseGate`).
6. **Shown soberly.**
   - The capture dialog states the costs before the choice, in the same plain style as the others, with no heroic or celebratory text and no sound sting.
   - The follow-up cards are sourced event cards in the house tone: calm, specific, no melodrama (AGENTS.md "Tone").
   - No invented quotes. No image of real victims unless it meets the event-image ruling and sensitivity review.
7. **Owner decision (D-F1).** A sourced deport card necessarily depicts displacement, so it conflicts with the M3 rule "Lydda and Ramle appear as military events only" (docs/m3-rulings.md). The owner chooses which rule governs, and how.

### 4.2 The Arab forces as units

- **Names and identity.**
  - Use each force's own name, and nothing generic: the Arab Legion (Transjordan), the Army of the Holy War, the National Guard or local garrisons, as #228 and #233 already list.
  - "Palestinian militia" is the GDD's working label. The card names the specific formation where a source does.
- **Accuracy.**
  - Uniforms, equipment and markings are sourced to the same standard as the IDF units (docs/units.md "Sources"), with era-correct figures and models of the same quality and care.
  - Starting positions and reinforcements in Historical mode come from the #226–#233 research. They are never invented.
- **Gap in the GDD's roster.** The 1948 events include the southern front (`operation_yoav`, `operation_horev`, `armistice_egypt`), but the GDD lists only two enemy unit types. Either Egypt's forces get a unit type, or that front stays in events only (D-G1).
- **Dignity.**
  - No caricature, slurs, or dehumanising names or poses.
  - The enemy AI pursues its own goals (CONTENT_POLICY §1, "computer-run actors with their own goals").
  - Its casualties are reported as soberly as the player's.
  - Civilian figures are never combat units (#336 already holds this for its models).
- **Review.** A sensitivity review of the unit cards and art before shipping, as #226 already requires.

### 4.3 Capturing soldiers as a bonus

The GDD's objective 1 gives bonus points for capturing enemy soldiers. Specified so that it cannot reward harm:
1. **Who can be captured.** Only enemy **combatant** units, when an attack forces a surrender (an outcome of the combat rules). Residents can never be captured, and capture is never an action aimed at a settlement's people (the GDD's "distinct states").
2. **No reward for killing.** Kills and enemy casualties never score.
3. **The bonus comes at the return, not the capture.** Prisoners are held with Food upkeep. They are not labour, Money or a bargaining resource. Points are awarded when they are returned in the exchange after an armistice (a sourced event; the dates need sources). Any loss while they are held is a cost.
4. **Wording.** The bonus is framed as ending fighting with fewer lives lost. Prisoners are counted in the score, and nothing on screen celebrates the capture.

### 4.4 Every historical claim sourced

- **Objective cards** each need:
  - a sourced reference date and event;
  - a sourced image under the event-image ruling (docs/event-images.md);
  - a sourced account.
- **Dated milestones.** For "absorb immigrants", the GDD itself asks for a dated, sourced milestone.
- **The railway objective needs care.** The Tel Aviv–Haifa railway's historical completion date must be sourced. If it falls after the MVP window, "earlier than history" compares against a date after the game ends. The owner should know before choosing the card (D-B3).
- **Sourcing for every named place, number and date:**
  - site names, founding dates and positions;
  - corridor routes;
  - unit identities and positions;
  - city starting values that claim to be historical.
- **Label design values.** Balance values and counterfactuals are labelled as design assumptions in YAML comments, as `rules.yaml:1` does.
- **Hula drainage.** "Dry swamp" and the existing `hula_drainage` event (window 1951-03-07) must not contradict each other (D-B4).
- **Lint.** Each new GDD feature section uses `docs/gdd/TEMPLATE.md` and passes `gdd_lint.py`. Each rule gets an `R-` ID in `docs/rules/` with a citing test (`rule_ids.py`).

## 6. Phased build plan

Sizes assume the current agent-driven pace, one reviewed PR at a time per track: S = 1–3 days, M = 1–2 weeks, L = 3–4
weeks, XL = 6–8 weeks. Each phase ends with a playtest by the controller and a short ruling log, as M3 did.

### Phase 0: owner decisions (S, owner time)

- **Scope:** decide group A (D-A1 to D-A7), plus D-B1 and D-E1. Approve this plan.
- **Output:** a dated "GDD v0.1 rulings" section, appended by the owner or with the owner's approval (this document does not edit the GDD).
- **Then:** feature sections in `docs/gdd/` and `R-` IDs in `docs/rules/` for the Phase 1 rules.

### Phase 1: the vertical slice, behind the switch (M–L, 6–8 PRs)

**Scope.**
1. **Monthly turns as data.** The `turn_lengths` key and `TurnLengthFor(c, date, rung)`, the #81 design without the yearly turn.
   The default reproduces today's table.
2. **The switch and state scaffolding.** `systems.loop`, the new `GameState` fields with omit-at-default hashing, `Clone`
   and `Describe`, save schema 2 with the `ruleset` line, and the five command touch-points. The goldens do not move.
3. **One city.** Housing capacity and condition, job slots, and civilians and refugees as counts (per D-A2). `AssignWorkers`.
   Money from jobs. Social cohesion from housing and employment. Arrivals land in the city.
4. **Training.** One military camp and one Hakhshara. Civilian to recruit, and civilian to halutz, over N turns (no combat yet:
   a recruit is a count).
5. **One pioneer action.** "Build yishuv" at one designated site from `sites.yaml`, over N turns. On completion it appears on the map with its
   name (a placement and a kit).
6. **One objective card.** "First new yishuv": the completion card with a sourced date, image and text, and a score with the
   timing bonus.
7. **Minimal UI.** City panel, assign and train buttons, a site build button, the objective card through the event card, and
   the score on the HUD. Every number comes from sim helpers.

**Files and systems.**
- **Sim:** `SimTime.cs`, `SecuritySystem.cs`, `Simulation.cs`, `GameState.cs`, `Commands.cs`, `SaveGame.cs`,
  `AttentionSystem.cs`, `Content.cs` and `ContentLoader.cs`, plus new `Cities.cs`, `Training.cs`, `Projects.cs`,
  `Objectives.cs` and `TurnResolver.cs`.
- **Content:** new `cities.yaml`, `sites.yaml`, `objectives.yaml` and `unit_types.yaml` (population types only).
- **Tests:** a test content overlay.
- **Unity:** `SimBridge.cs` (`Key`, `Validate`), `InfoPanelPresenter.cs`, `HudPresenter.cs`, `EventCardPresenter.cs`, and
  `strings.en.yaml`.

**Tests and goldens.**
- One test per rule, citing its `R-` ID.
- Save round-trip of every new command.
- Clone independence.
- An omit-at-default test: with the switch off, `Describe()` is unchanged byte for byte.
- `Hash1950`, `Hash1952`, `smoke5` and the scenarios unchanged.
- New overlay goldens `mvp-slice` and `scenario-mvp-absorb-first`.
- Unity EditMode tests for the panel (say in the PR if they were not run).

**Risks.**
- Inventing values. Mitigation: every balance number is the owner's or labelled as a placeholder in a test overlay, never in
  real content.
- UI scope creep.
- Contributors' era PRs touching `Content.cs` at the same time. Mitigation: merge them first (§7).
